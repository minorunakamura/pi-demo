# ブラウザ版リバーシ 実装計画

## 目的

PCのChromeで、人間がCPUと起動直後から1局遊べ、パス・終局・再戦まで迷わず操作できるリバーシを作る。

入力設計は `docs/designs/reversi.md`。特に「確認済みの要件と範囲」「対局の流れ」「CPUの判断」「画面の方針」「残る不確実性と確認する観点」を実装・検証の根拠とする。本計画はその設計案を具体化するもので、目的・責務・対象外の変更は行わない。

## 調査で確認した現状

- リポジトリには入力設計のみがあり、既存のソース、package設定、テスト、チェックコマンド、プロジェクト固有の規約はない。mainにはまだcommitがない。既存利用者のデータ移行や呼び出し元の修正は不要。
- 調査環境はNode `v24.21.0`、npm `11.19.0`。調査時のVite安定版 `8.3.4` のNode要件 `^20.19.0 || >=22.12.0` に適合する。
- 性能、CPUの楽しさ、実際のChrome操作は未検証。実装後の確認項目とし、調査済みの事実とは扱わない。

## 要件・決定事項

### 対局

- 標準8×8、プレイヤーは黒・先手、CPUは白・後手。画面表示時点で初期対局を開始する。
- 人間とCPUで同じルールを使い、8方向の反転、手番、強制パス、終局、石数、勝敗を判定する。
- 合法手のない側は理由を文字で表示して自動パスする。双方が打てなければ空きマスが残っていても終局する。同数は引き分け。
- 非合法・範囲外・占有済みマス、CPU手番中、終局後の着手入力では対局状態を変えない。
- 対局中は「最初から」、終局後は「もう一度遊ぶ」で即座に初期状態へ戻す。以前のCPU応答は新しい対局へ反映しない。
- 状態はブラウザのメモリ内のみ。リロードで初期状態になる。

### CPU

- 最大2着手先までの固定したminimaxを使う。通常はCPUの候補とプレイヤーの応手を読む。時間が余っても3着手以上には深くしない。
- まず全候補の1着手読みを完了し、次に全候補の2着手読みを行う。探索途中のパスは着手数に数えず、共有ルールが返す次の手番に従い、同じ側が続けて打つ場合も扱う。双方が打てなければ即座に終局評価する。
- 白視点で角・双方の合法手数・石数を評価する。初期値は角差×100、合法手数差×10、石数差×1、空き16以下では石数差×5とする。終局は勝ちを+10000、負けを-10000に石数差を加え、引き分けを0とし、非終局の評価より勝敗を優先する。
- 同点は盤面の行優先順で最初の候補に固定する。意図的な悪手、乱数、難易度設定は加えない。評価の係数は実際の対局で調整可能だが、評価要素や最大深さは本計画の範囲内に保つ。
- 探索前に合法手を1つ確保する。計算予算は最大800msを初期値とし、単調増加の時計で探索の小さな処理単位ごとに期限を確認する。
- 2着手読みが全候補について完了しなければ、完了済みの1着手読みの結果を採用する。1着手読みも未完了なら最初に確保した合法手を使う。部分的な深い探索結果を完成済みの結果へ混ぜない。
- CPU探索はWeb Worker内の仮の盤面で行い、入力の盤面を変更しない。

### 画面・操作

- 中央の大きな盤面と、手番、黒白の石数、CPU思考中、パス、勝敗、再開始操作を1画面に置く。最終盤面は終局後も残す。
- 合法手と直前の着手を、色だけでなく記号・枠・説明でも区別する。
- 盤面の各マスには座標と石の状態が分かるaccessible nameを付ける。native buttonを基本とし、Tab移動とEnter/Spaceでマウスなしでも合法手を選べる。focusを明示し、再描画で操作中のfocusを不用意に失わない。
- 思考・パス・終局等は文字で示し、status領域の`aria-live`を使う。パスの説明は次の手番表示と併記するなど、即時の状態遷移で読めなくならないようにする。
- CPU思考中も再開始ボタンは操作できる。配色・余白の詳細は実装時に見やすさを優先して決める。

## 制約・対象外

- PCのChrome、ローカルサーバー経由での利用のみ。スマートフォン、他ブラウザ、HTMLの直接起動は対象外。
- Vite＋素のTypeScript＋HTML/CSS。UI framework、ゲーム用バックエンド、DB、外部AIサービス、runtime依存は追加しない。
- 保存・復元、戦績、対人戦、オンライン対戦、難易度選択、色選択、待った、深い探索、Worker pool、汎用状態管理基盤は追加しない。
- 本Planningでは本番コード、依存関係のインストール、workerによる実装、commit、push、merge、release、deployを行わない。実装はWork Itemごとの新しいImplementationセッションで行う。
- OS停止、バックグラウンド制限、ブラウザのスケジューリング遅延まで含めた厳密な1秒保証はしない。通常の前面タブで1秒以内を実測する要件は維持する。

## 実装方針

### 構成と開発チェック

必要なファイルの目安は次のとおり。役割ごとに分けるが、将来用の層・interface・設定は増やさない。

| ファイル | 責務 |
| --- | --- |
| `package.json`、`package-lock.json`、`tsconfig*.json`、`.gitignore` | 開発・build・型検査・テスト、生成物の除外 |
| `index.html`、`src/main.ts`、`src/style.css` | DOM、入力、描画、Workerのブラウザ接続 |
| `src/rules.ts` | 盤面型、初期状態、合法手、着手・反転、パス・終局、石数・勝敗 |
| `src/cpu.ts` | DOM/Workerに依存しない時間制限付き手選択 |
| `src/cpu.worker.ts` | CPUリクエストを受け、選択結果を返信する薄いWorker入口 |
| `src/game.ts` | 人間の着手、CPU応答、再開始、要求の失効を扱う小さな対局controller |
| `tests/*.test.ts` | ルール・CPU・対局controllerの公開境界テスト |
| `README.md` | セットアップ、操作、チェック、性能・対局確認方法と確認結果 |

- npmを使う。dev依存はVite、TypeScript（5.8以上で採用Viteと互換のある安定版）、`@types/node`（Node24系）のみにする。導入時の実際のバージョンをlockfileに保存する。
- Node24.21.0を確認基準としてREADMEに明記する。`package.json`は`type: module`。相対importは`.ts`まで記述し、`import type`を使う。`enum`等の実行時変換を要するTypeScript構文は使わない。
- `strict`、`noEmit`、`isolatedModules`、`erasableSyntaxOnly`、`.ts`拡張子import対応を有効にする。ブラウザ、Worker、Nodeテストのglobal型が混ざらないよう、対象と`lib`/`types`を分けた必要最小限のtsconfigを用意する。Viteの変換だけを型検査の代わりにしない。
- コマンドは`npm run dev`、`npm test`（`node --test tests/*.test.ts`）、`npm run typecheck`、`npm run build`、`npm run preview`。test runnerやDOMエミュレーターは追加しない。

### 共有ルールと公開境界

- 盤面は64マスの単純な配列とし、空/黒/白を明示する。座標は左上A1、行優先とする。初期配置は白D4/E5、黒E4/D5。黒の初期合法手はD3/C4/F5/E6。
- `rules.ts`は初期化・合法手列挙・着手・手番正規化・集計を公開し、画面、CPU、controllerはこの処理を共用する。合法でない着手を防ぎ、元の状態を変更しない。
- 着手後の手番正規化でパス・終局を確定する。盤面、手番、進行状態、直前の着手、表示すべきパス情報を保持し、石数や合法手等の導出可能な値を重複管理しない。
- `cpu.ts`は現在の盤面から白の合法手または合法手なしを返す。テストでは時計と計算予算を渡せるようにし、実時間の遅延を使わず期限切れを再現する。
- `game.ts`の公開境界は人間の着手、再開始、状態の取得/通知、CPU実行との接続とする。CPU実行境界だけを差し替え可能にして、DOMなしで遅延応答・失敗・取消の順序をテストする。汎用イベント基盤は作らない。

### Worker・時間制限・再開始の安全性

- `new Worker(new URL('./cpu.worker.ts', import.meta.url), { type: 'module' })`というVite標準の生成方式を使い、CPU手番ごとにWorkerを1つ起動し、完了時に終了する。
- main側でもCPU手番開始から暫定900msで期限を監視する。探索の800msとは別に、起動・通信・描画の余裕を残す。1秒を待ち切ってから代替手を選ぶ設計にしない。
- Workerの起動失敗、`error`、`messageerror`、期限超過、不正な応答では思考を終了し、共有ルールで確認済みの合法な代替手を一度だけ着手する。思考中のまま停止させない。
- 応答は現在有効な要求に対応し、現在もCPU手番で、結果が現局面の合法手である場合だけ採用する。完了・失敗・timeoutが競合しても最初の確定だけを反映する。
- 再開始では要求を先に失効させ、timer解除とWorker終了を行って初期状態へ戻す。終了後に届いた古いcallbackも有効性確認で捨てる。`terminate()`後の完了通知には依存しない。
- 900ms/800msは初期値。Chromeの実測で起動・描画を含め1秒を超える場合、計算予算・監視期限を短くして再測定する。タイマー自体に実時間保証がないことはREADMEにも示す。

## テスト方針

ルール・CPU・対局controllerはTDDで進める。Implementationで既存の`tdd` Skillを読み、1件の失敗テスト→最小実装の縦スライスを繰り返す。本Planの承認で、以下の公開seamをテスト対象として確認する。内部関数や探索順序の実装詳細は固定しない。

| 公開seam | 主に捕捉する問題 | 対象外 |
| --- | --- | --- |
| 共有ルールの初期化・合法手・着手/進行・結果 | 反転、入力拒否、パス、終局、集計の誤り | DOMと実時間 |
| CPUの手選択 | 非合法手、パスの読み違い、期限切れfallback、元盤面の破壊 | 楽しさと実機の応答時間 |
| 対局controllerの着手・再開始・CPU応答 | 入力制限、旧応答、二重反映、失敗時の停止 | 実際のWorker通信と描画 |

最低限のテスト:

1. 初期石数2対2と黒の4合法手。既知の小局面で縦横斜め・複数方向の反転、盤端での行またぎ防止。占有/挟めない/範囲外の拒否と入力盤面の不変性。
2. 黒/白それぞれの片側パス、パス後に同じ側が続けて着手、盤面が埋まる終局、空きが残る双方手なしの終局、黒勝ち/白勝ち/引き分け。
3. CPUが常に合法手を返すこと、合法手なし、角を取れる既知局面と終局勝敗を優先すべき局面、2着手目にパス/終局する局面、元盤面の不変性。
4. 注入時計で探索開始直後の期限切れ、1着手読み完了後の期限切れ、2着手読みの途中打切り、全候補完了を再現し、未完了の深い結果を採用しないことを既知の期待手で確認する。時計呼出回数そのものはassertしない。
5. 制御可能なCPU実行境界を通じ、人間の連打/CPU手番中/終局後の入力拒否、CPU失敗・timeout・不正応答の代替手、完了とtimeoutの競合、思考中の再開始と旧応答、再開始の連続実行、正常応答後の不要なtimer/要求の残存防止を確認する。

期待値は設計または手計算した小局面から得る。CPU自身の評価関数で期待値を再計算するだけのテストは作らない。DOM/実WorkerはNodeで無理に模倣せず、以下のChrome確認で補う。

## 完了条件

- 新規checkoutからREADMEどおりに`npm ci`、起動、対局、終局、再戦まで行える。
- `npm test`、`npm run typecheck`、`npm run build`がすべて成功する。
- プレイヤーとCPUが共有ルールで動き、パス・勝敗・再開始・旧応答破棄のテストが通る。
- Chrome上でマウスとキーボードの双方で遊べ、合法手、直前の着手、手番、石数、思考、パス、勝敗が識別できる。思考中の再開始で状態が壊れない。
- 通常の前面タブの対象PC Chromeで、初回Worker起動を含む序盤・中盤・終盤のCPU手番を計測し、確認した全手番で手番開始から着手表示まで1秒以内である。環境・局面・最大値・使用予算を記録する。満たせなければ完了としない。
- 数局を実際に遊んで、角・選択肢・終局勝敗を無視する明らかに不自然な手が目立たず、気軽に勝負できるかをユーザーと確認する。楽しさを自動テスト合格だけで認定しない。
- 必要なテスト、fixtures、設定、README、build後の確認まで含めて完成させ、未検証項目が残れば明示する。

## 動作確認方法

1. `npm ci`→`npm test`→`npm run typecheck`→`npm run build`。README記載のNode/npm環境で実行し結果を記録する。
2. `npm run dev`でPC Chromeから開き、初期配置、不正入力、合法手の表示、着手と反転、CPU思考表示、CPU応答、石数、直前手を確認する。DevTools consoleにエラーがないことも確認する。
3. Tab/Enter/Spaceだけで着手・再開始でき、focusが見え、描画後も適切に残ることを確認する。CPU手番中は盤面に着手できず、再開始は操作できることを確認する。
4. 思考中の「最初から」を繰り返し、旧対局の白石が初期盤面へ混ざらないことを実Workerで確認する。速く完了して再現しにくい場合だけ、一時的なDevTools breakpoint等で応答を遅らせ、検証後に解除する。
5. 自動テストで使う既知局面を、開発時限定の一時harnessからcontrollerへ与え、人間/CPU双方のパス、双方手なし、引き分け、終局後の操作と再戦を画面でも確認する。盤面編集機能やproductionの隠し入口は追加しない。
6. 前面タブ、CPU throttlingなしで序盤・中盤・終盤を含む10局面以上（初回Worker起動、候補の多い局面、パスを伴う局面を含む）を計測する。DevTools Performanceまたは一時的なperformance marksで、CPU手番開始から着手の描画までを確認する。平均だけでなく最大値を記録し、1秒を超えたら予算を調整して再検証する。恒久的な計測基盤は作らない。
7. 人間として数局遊び、CPUの不自然な手・強さを確認する。必要なら評価係数のみを調整し、テストと時間計測を再実行する。
8. `npm run preview`でbuild成果物を開き、Worker chunkの読込み、1局の進行、再開始、consoleエラーなしを確認する。開発サーバーだけの成功で終えない。

## リスクと引継ぎ

- 2着手読みと単純な評価で楽しさは保証できない。新しい探索方式へ黙って拡張せず、まず係数を調整する。範囲外の変更が必要なら再計画する。
- Workerでも実時間の上限保証はできない。測定結果は対象環境での確認であり、全PCやOS停止時の保証ではない。
- 基本設計の更新を必要とする仕様変更は現時点ではない。設計書は変更しない。
- Approved Planを`docs/plans/reversi.md`へ正式保存し、Work Itemsは別途ユーザーに分割・保存公開を確認する。全Work ItemからこのPlanを参照可能にする。Implementationは新しいセッションへ引き継ぐ。
